## Prompt 注入攻击如何防御？

**来源：** 快手AI Agent开发一面

### 核心要点

- **输入隔离：** system / user / tool observation 严格分隔；XML / JSON tag 边界。
- **指令层级：** system 声明「用户输入不可覆盖系统指令」；但不可 100% 依赖。
- **预处理：** 检测 jailbreak 模式、敏感指令、URL / 隐藏文本；长度限制。
- **输出约束：** schema 校验、禁止 exfiltration 工具、最小权限 tool list。
- **纵深防御：** 敏感操作 Human-in-the-loop；独立 moderation model；审计日志。

### 与前端工程结合的角度

- 用户粘贴内容默认视为 untrusted；富文本 strip hidden instruction。
- 展示「AI 可能出错」+ 不渲染 raw HTML from model 防 XSS。

### 面试加分项

- 举例 indirect prompt injection（恶意网页被 browse tool 加载）。
- 引用 OWASP LLM Top 10（LLM01 Prompt Injection）。

## 工具调用的安全控制如何实现？

**来源：** 快手AI Agent开发一面

### 核心要点

- **最小权限：** 每个 tool 只暴露必要 scope（read-only DB、sandbox FS）。
- **Allowlist：** 可调 API 域名 / 命令白名单；参数 schema 强类型。
- **确认门：** 写操作、外发邮件、支付需用户确认。
- **沙箱：** 代码执行 Docker / WASM / gVisor；网络 egress 限制。
- **审计：** 谁、何时、调了什么 tool、参数、结果 hash。

### 与前端工程结合的角度

- OAuth scope 与 tool 权限对齐；UI 展示当前 Agent「可访问的资源」。
- 敏感 tool call 弹窗展示 JSON 参数供用户 edit 后再执行。

### 面试加分项

- 说明 capability-based security vs ACL。
- 提到 Computer Use 场景的 desktop sandbox 方案。

## 工具调用失败、超时了怎么办？

**来源：** 分享一下我面试Agent岗位时被问到的问题、某大厂 RAG+Agent 面经

> 完整可运行实现见 [手写代码题 · 工具调用统一封装](手写代码题.md#工具调用统一封装带重试与超时)。

### 核心要点

- **统一封装：** try/catch → 结构化 `{ error, code, retryable }` 喂回 LLM。
- **重试：** 幂等操作 retry ≤2，exponential backoff；非幂等不自动 retry。
- **超时：** 单 tool timeout + 整体 agent timeout（如 30s）。
- **降级：** 主 API 挂了切备用端点；缓存 stale data；跳过非关键步骤。
- **LLM 决策：** 将结构化错误（如 `Error: 超时`）喂回模型，让它决定 retry / 换 tool / 告知用户。
- **面经参数：** 单 tool retry ≤2；整体 Agent timeout 约 30s；关键工具有备用 API 降级。

### 与前端工程结合的角度

- SSE 推送 tool_error 事件；UI 显示失败步骤 + 重试按钮。
- AbortController 取消长时间 tool call。

### 面试加分项

- 区分 timeout vs 4xx vs 5xx 处理策略。
- OpenTelemetry span 标记 tool latency 瓶颈。

```typescript
// 统一封装：错误结构化后喂回 Agent，而非抛异常中断会话
async function runTool<T>(fn: () => Promise<T>, retries = 2) {
  for (let i = 0; i <= retries; i++) {
    try {
      return { ok: true as const, data: await Promise.race([fn(), timeout(30_000)]) };
    } catch (e) {
      if (i === retries) return { ok: false as const, error: String(e), retryable: true };
    }
  }
  throw new Error("unreachable");
}
```

## 分布式令牌桶限流是什么？

**来源：** 快手AI Agent开发一面

> 完整可运行实现见 [手写代码题 · 令牌桶限流](手写代码题.md#分布式令牌桶限流单机--redis-思路)

### 核心要点

- **令牌桶：** 固定速率往桶里放令牌；请求消耗令牌；桶满可突发（burst）。
- **分布式：** 令牌计数存 Redis（Lua 脚本保证原子性）；多实例共享配额。
- **Agent 场景：** 限制 LLM API QPS、单用户 daily token、tool call 频率。
- **参数：** rate（tokens/s）、capacity（burst size）。

### 与前端工程结合的角度

- 429 时前端 exponential backoff + 友好「请求过于频繁」。
- 展示剩余 quota（如每日 AI 次数）提升透明度。

### 面试加分项

- Redis CELL / Gauva RateLimiter 实现。
- 与 Agent 成本管控、多租户 fair scheduling 结合。

## 漏桶算法是什么？

**来源：** 快手AI Agent开发一面

> 完整可运行实现见 [手写代码题 · 漏桶算法](手写代码题.md#漏桶算法leaky-bucket)

### 核心要点

- **原理：** 请求进漏桶，以**固定速率**流出处理；桶满则丢弃或排队。
- **特点：** 输出速率严格恒定，平滑 burst；不允许大的突发（与令牌桶不同）。
- **场景：** 下游处理能力固定（如写 DB、第三方 API 严格 QPS）。
- **实现：** 队列 + 定时器 / 时间戳计算 leak。

### 与前端工程结合的角度

- 理解即可；前端队列化用户操作（debounce 提交）类似平滑请求。

### 面试加分项

- 对比令牌桶：漏桶输出更平滑；令牌桶允许 controlled burst。
- 说明 leaky bucket vs sliding window log 实现差异。

## 滑动窗口算法如何实现？与令牌桶有何区别？

**来源：** 快手AI Agent开发一面

> 完整可运行实现见 [手写代码题 · 滑动窗口](手写代码题.md#滑动窗口限流)

### 核心要点

- **滑动窗口：** 统计最近 W 时间窗内请求数 / token 数；超限拒绝。
- **实现：**  Redis ZSET 存 timestamp score 滑动清理；或 fixed window + 加权近似。
- **vs 令牌桶：** 滑动窗口硬限制窗内总量，无 burst 容忍（除非窗内均匀）；令牌桶允许 burst 借未来额度。
- **vs 漏桶：** 滑动窗口限制入口；漏桶限制出口速率。

### 与前端工程结合的角度

- 「每分钟最多 N 次生成」用 sliding window；前端 countdown 提示重试时间。

### 面试加分项

- 滑动窗口 vs 固定窗口边界双倍突发问题。
- Agent 场景按 token 数而非 request 数限流更准确。

## 布隆过滤器（Bloom Filter）是什么？

**来源：** 快手AI Agent开发一面

> 简易实现见 [手写代码题 · 布隆过滤器](手写代码题.md#布隆过滤器简易实现)。

### 核心要点

- **结构：** 位数组 + 多个 hash 函数；插入元素置位；查询全 1 则「可能存在」。
- **特性：** 无 false negative（未插入必不存在）；有 false positive；不可删除（除非 Counting Bloom）。
- **Agent 场景：** 快速判断 doc_id / cache key 是否可能存在，减少 DB / 向量库查询；URL 去重、已处理 chunk 过滤。

### 与前端工程结合的角度

- 纯后端组件；前端理解有助于讨论「为什么首次查慢、二次快」（negative cache + bloom）。

### 面试加分项

- 参数 m、n、k 与 false positive rate 关系。
- 说明不适合需要精确删除的场景（用 Cuckoo filter 等）。

## 数据库索引失效的情况有哪些？like 查询会导致索引失效吗？

**来源：** 快手AI Agent开发一面

### 核心要点

- **失效场景：** 对列做函数 / 运算、`OR` 连接不同列、隐式类型转换、 `%xxx` 左模糊、不符合最左前缀联合索引、优化器判断全表扫描更优、低选择性列。
- **like：** `%keyword` 或 `%keyword%` 通常无法走 B-tree 索引；`keyword%` 前缀匹配**可以**用索引。
- **Agent 场景：** 元数据 filter（tenant_id、doc_type）需索引；全文检索用 ES / BM25 而非 SQL like。

### 与前端工程结合的角度

- 管理后台筛选字段设计影响后端索引；避免随意 `%search%` on 大表。

### 面试加分项

- 覆盖索引、EXPLAIN 分析习惯。
- pgvector HNSW 索引与 B-tree 分工。

## 大模型生成参数：温度、top-k、top-p 在不同业务场景如何配置？

**来源：** 字节AI Agent后端面经

### 核心要点

- **Tool call / SQL / JSON：** temperature 0–0.2，低 top_p（0.1–0.5），求 deterministic。
- **客服 FAQ：** temperature 0.3–0.5，平衡一致性与自然度。
- **创意文案：** temperature 0.7–0.9，top_p 0.9。
- **top-k：** 与 top_p 一般二选一或同时用但保守；Agent 默认 low randomness。

### 与前端工程结合的角度

- 产品「精确 / 平衡 / 创意」三档映射后端参数 preset。
- 开发者高级设置暴露 temperature slider。

### 面试加分项

- 说明 same seed 不完全 reproducible（GPU nondeterminism）。
- A/B 不同参数对 task success rate 影响。

## 业务任务拆分的设计思路？

**来源：** 字节AI Agent后端面经

### 核心要点

- **分解原则：** MECE、依赖顺序、每步可验证、粒度匹配 tool 能力。
- **模式：** sequential pipeline、parallel fan-out、map-reduce（千条数据分批）。
- **Agent 实现：** planner 输出 DAG / todo list；executor 逐步完成；state 存中间结果。
- **人工检查点：** 关键子任务完成后 pause for approval。

### 与前端工程结合的角度

- 任务列表 UI 与 backend task state 双向同步；子任务失败可单独 retry。

### 面试加分项

- 对比 microservice choreography vs orchestration。
- 举例：发版流程拆成 lint → test → build → deploy。

## 一千条数据求和，如何设计 Agent 处理流程？

**来源：** 快手AI Agent开发一面

> Map-Reduce 代码实现见 [手写代码题 · 大批量求和](手写代码题.md#大批量数据求和map-reduce禁止塞入-llm-context)

### 核心要点

- **不要让 LLM 心算 1000 条：** 工具化 / 代码化执行。
- **流程：** Agent 理解意图 → 调用 `sum(data)` 或生成 Python/SQL → sandbox 执行 → 返回结果。
- **大数据：** map-reduce 分批 sum 再 aggregate；流式读取防 OOM。
- **校验：** 抽样人工核对；结果 order-of-magnitude sanity check。

### 与前端工程结合的角度

- 表格上传 CSV → 后端 pandas sum；前端只展示结果与过程 log，不让模型逐行读。

### 面试加分项

- 强调 code interpreter 模式 vs 把 1000 行塞进 prompt。
- 提到 batch size 与 timeout 配置。

## 大模型网关（LLM Gateway）是什么？Agent 系统为什么需要？

**来源：** 字节AI Agent后端面经

### 核心要点

- **定位：** 位于业务与多家模型 API 之间的统一接入层，负责路由、鉴权、限流、计费、日志与协议适配。
- **核心能力：** 多模型 fallback（GPT → Qwen 降级）、OpenAI-compatible 协议转换、API Key 集中管理、按租户 quota 限流、请求/响应审计。
- **常见方案：** LiteLLM、OneAPI、Portkey、自研 Gateway（基于 Envoy / FastAPI middleware）。
- **Agent 价值：** Agent 多轮 + 多 tool 调用放大请求量，网关统一管控成本与 SLA，避免业务代码散落各家 SDK。

### 与前端工程结合的角度

- 前端只调自家 BFF，不直连模型 Key；网关对前端透明，但需处理 429/503 统一错误码与 retry 提示。
- Admin 面板可经网关暴露「模型用量 / 费用」图表，前端用同一套 REST 拉 metrics。

### 面试加分项

- 说明 model router：简单 query 走小模型、复杂推理走大模型，网关层做 latency-aware routing。
- 提到 stream 透传：网关需正确处理 SSE chunk 转发，不能 buffer 整包。

## 为什么偏向手写 Agent 而非纯框架？（工程视角补充）

**来源：** 字节AI Agent后端面经

### 核心要点

- 见 Agent 框架篇 LangChain 对比；工程化侧补充：**可测试性**（纯函数节点）、**可观测**（统一 trace id）、**发布**（灰度 skill / prompt 版本）、**合规**（审计钩子框架未必内置）。

### 与前端工程结合的角度

- 与前端 monorepo 自研组件库同理：框架加速 0→1，自研保障 1→N 可控。

### 面试加分项

- 混合策略：LangGraph 编排 + 自研 tool registry + 自研 eval pipeline。
