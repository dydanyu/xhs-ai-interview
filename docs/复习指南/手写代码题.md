## 分布式令牌桶限流（单机 + Redis 思路）

**来源：** 快手AI Agent开发一面

### 题目要点

- 固定速率向桶中放入令牌；请求消耗令牌；桶满时可突发（burst）。
- 分布式场景需 Redis + Lua 保证原子性；Agent 场景用于 LLM API QPS、单用户 token 配额。

### 可运行实现（单机 TypeScript）

```typescript
/** 单机令牌桶：rate=每秒补充令牌数，capacity=桶容量（最大突发） */
class TokenBucket {
  private tokens: number;
  private lastRefill: number;

  constructor(
    private rate: number,      // tokens / second
    private capacity: number,
  ) {
    this.tokens = capacity;
    this.lastRefill = Date.now();
  }

  /** @returns true=允许通过，false=被限流 */
  tryConsume(count = 1): boolean {
    this.refill();
    if (this.tokens >= count) {
      this.tokens -= count;
      return true;
    }
    return false;
  }

  private refill() {
    const now = Date.now();
    const elapsed = (now - this.lastRefill) / 1000;
    this.tokens = Math.min(this.capacity, this.tokens + elapsed * this.rate);
    this.lastRefill = now;
  }
}

// 用法：LLM 网关限制 10 QPS，允许 burst 20
const limiter = new TokenBucket(10, 20);
export function allowRequest() {
  return limiter.tryConsume(1);
}
```

### Redis 分布式伪代码（面试口述）

```lua
-- KEYS[1]=bucket_key  ARGV[1]=rate  ARGV[2]=capacity  ARGV[3]=now  ARGV[4]=requested
local tokens = tonumber(redis.call('GET', KEYS[1] .. ':tokens') or ARGV[2])
local last = tonumber(redis.call('GET', KEYS[1] .. ':ts') or ARGV[3])
local delta = math.max(0, ARGV[3] - last)
tokens = math.min(ARGV[2], tokens + delta * ARGV[1])
if tokens >= ARGV[4] then
  tokens = tokens - ARGV[4]
  redis.call('SET', KEYS[1] .. ':tokens', tokens)
  redis.call('SET', KEYS[1] .. ':ts', ARGV[3])
  return 1
end
return 0
```

### 复杂度与边界

- **时间复杂度：** O(1) 每次 tryConsume。
- **边界：** 长时间 idle 后首次请求可消耗最多 `capacity` 个令牌（突发）；多实例必须用 Redis 共享状态；按 token 数限流时 `count` 传预估 completion tokens。

### 与前端工程结合的角度

- 收到 HTTP 429 时前端 exponential backoff；Admin 面板展示 quota 剩余。
- BFF 层统一限流，避免浏览器直连模型 Key 绕过配额。

### 面试加分项

- 对比 Guava RateLimiter、Redis Cell 模块。
- Agent 多租户 fair queue：每 tenant 独立 bucket + 全局 bucket 双层限流。

## 漏桶算法（Leaky Bucket）

**来源：** 快手AI Agent开发一面

### 题目要点

- 请求进入漏桶，以**固定速率**流出处理；桶满则拒绝或排队。
- 输出速率严格恒定，适合下游 QPS 固定的第三方 API。

### 可运行实现

```typescript
/** 漏桶：leakRate=每秒处理请求数，capacity=桶容量（排队上限） */
class LeakyBucket {
  private queue: number[] = []; // 存请求到达时间戳，简化版用计数
  private lastLeak: number = Date.now();
  private water = 0;

  constructor(
    private leakRate: number,  // requests / second
    private capacity: number,
  ) {}

  /** @returns true=接受并排队处理，false=桶满拒绝 */
  allow(): boolean {
    this.leak();
    if (this.water >= this.capacity) return false;
    this.water += 1;
    return true;
  }

  private leak() {
    const now = Date.now();
    const leaked = ((now - this.lastLeak) / 1000) * this.leakRate;
    this.water = Math.max(0, this.water - leaked);
    this.lastLeak = now;
  }
}

// 下游写库最多 5 req/s，桶容量 10（最多积压 10 个）
const bucket = new LeakyBucket(5, 10);
```

### 复杂度与边界

- **时间复杂度：** O(1) 均摊（浮点 leak 计算）。
- **边界：** 桶满时选 **拒绝（429）** 还是 **阻塞排队** 需产品决定；Agent tool call 建议拒绝 + 告知用户重试，避免长时间 hang。
- **vs 令牌桶：** 漏桶不允许大的出口突发；令牌桶允许 controlled burst。

### 与前端工程结合的角度

- 前端请求队列 + debounce 提交，类似客户端侧「漏桶」平滑 burst。
- 工具调用 pending 队列 UI 展示排队位置（若采用排队策略）。

### 面试加分项

- 说明漏桶平滑 traffic 保护下游 DB；令牌桶更适合允许短时 burst 的 LLM API。

## 滑动窗口限流

**来源：** 快手AI Agent开发一面

### 题目要点

- 统计最近 W 毫秒内的请求数 / token 数，超限则拒绝。
- 对比令牌桶：滑动窗口硬限制窗内总量，突发容忍度更低（除非窗口很大）。

### 可运行实现

```typescript
/** 滑动窗口：windowMs 内最多 maxRequests 次 */
class SlidingWindowLimiter {
  private timestamps: number[] = [];

  constructor(
    private windowMs: number,
    private maxRequests: number,
  ) {}

  allow(): boolean {
    const now = Date.now();
    // 清理窗口外记录
    this.timestamps = this.timestamps.filter((t) => now - t < this.windowMs);
    if (this.timestamps.length >= this.maxRequests) return false;
    this.timestamps.push(now);
    return true;
  }

  /** 距离下次可请求的毫秒数（前端 countdown 用） */
  retryAfterMs(): number {
    if (this.timestamps.length < this.maxRequests) return 0;
    return this.windowMs - (Date.now() - this.timestamps[0]);
  }
}

// 每分钟最多 60 次 Agent 对话
const limiter = new SlidingWindowLimiter(60_000, 60);
```

### Redis 实现思路（面试口述）

- **ZSET：** score=timestamp，每次 `ZREMRANGEBYSCORE key 0 now-window`，`ZCARD` 与 limit 比较，通过则 `ZADD`。
- **固定窗口 + 加权：** 内存更省但有边界双倍突发问题；滑动窗口更精确。

### 复杂度与边界

- **时间复杂度：** 数组版 O(n) 清理；生产用 ZSET 或环形计数器优化。
- **边界：** 固定窗口在窗口边界可能出现 2× burst；Agent 按 **token 数** 限流比按 request 数更准确。
- **vs 令牌桶：** 滑动窗口无「借未来额度」；令牌桶允许 burst 借 unused capacity。

### 与前端工程结合的角度

- `retryAfterMs()` 驱动 UI countdown「30 秒后可再试」。
- 429 响应头 `Retry-After` 与后端 limiter 对齐。

### 面试加分项

- 双层限流：滑动窗口（分钟级）+ 令牌桶（秒级 burst）。
- 说明 LLM Gateway 常见组合：tenant daily quota（固定窗口）+ API QPS（令牌桶）。

## 简化 ReAct Agent Loop

**来源：** 2026大模型Agent面试全攻略、字节AI Agent后端面经（现场实现类追问）

### 题目要点

- Thought → Action（tool call）→ Observation → 循环，直到 finish 或达 max_iterations。

### 可运行实现

```typescript
type Message = { role: "user" | "assistant" | "tool"; content: string };
type Tool = { name: string; fn: (args: Record<string, unknown>) => Promise<string> };

interface ReActResult {
  answer: string;
  steps: number;
}

/** 简化 ReAct：LLM 返回 JSON { thought, action?, args?, finish? } */
export async function reactLoop(
  llm: (messages: Message[]) => Promise<string>,
  tools: Record<string, Tool["fn"]>,
  userGoal: string,
  maxIter = 8,
): Promise<ReActResult> {
  const messages: Message[] = [{ role: "user", content: userGoal }];

  for (let step = 0; step < maxIter; step++) {
    const raw = await llm(messages);
    const parsed = JSON.parse(raw) as {
      thought: string;
      action?: string;
      args?: Record<string, unknown>;
      finish?: string;
    };

    messages.push({ role: "assistant", content: raw });

    if (parsed.finish) {
      return { answer: parsed.finish, steps: step + 1 };
    }

    if (!parsed.action || !tools[parsed.action]) {
      messages.push({ role: "tool", content: "Error: unknown tool" });
      continue;
    }

    const observation = await tools[parsed.action](parsed.args ?? {});
    messages.push({ role: "tool", content: observation });
  }

  throw new Error("max iterations exceeded");
}
```

### 复杂度与边界

- **时间复杂度：** O(maxIter × LLM_latency)；瓶颈在 LLM 与 tool IO。
- **边界：** 必须设 maxIter + 总 timeout；相同 action+args 重复 N 次应中断（循环检测）；JSON parse 失败走 self-heal retry。

### 与前端工程结合的角度

- 每轮 loop 推送 SSE 事件 `thought` / `tool_call` / `observation`，驱动 UI 时间线。
- AbortController 取消进行中的 loop。

### 面试加分项

- 对比 native function calling（OpenAI tool_calls）vs prompt-based JSON ReAct。
- 提到 LangGraph checkpoint 在 interrupt 后可 resume。

## SSE 流式响应解析器

**来源：** Agent 工程实践（前端常考）

### 题目要点

- 解析 `text/event-stream`：`event:` / `data:` / 空行分隔；支持半包、多 data 行、断线重连。

### 可运行实现

```typescript
/** 解析 SSE 字节流，yield { event?, data } */
export async function* parseSSE(
  body: ReadableStream<Uint8Array>,
): AsyncGenerator<{ event?: string; data: string }> {
  const reader = body.getReader();
  const decoder = new TextDecoder();
  let buffer = "";
  let event: string | undefined;
  let dataLines: string[] = [];

  const flush = function* () {
    if (dataLines.length === 0) return;
    yield { event, data: dataLines.join("\n") };
    event = undefined;
    dataLines = [];
  };

  while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    buffer += decoder.decode(value, { stream: true });

    const lines = buffer.split("\n");
    buffer = lines.pop() ?? "";

    for (const line of lines) {
      if (line === "") {
        yield* flush();
        continue;
      }
      if (line.startsWith("event:")) event = line.slice(6).trim();
      else if (line.startsWith("data:")) dataLines.push(line.slice(5).trim());
    }
  }
  yield* flush();
}

// 用法：fetch + parseSSE 驱动 Agent UI
// for await (const msg of parseSSE(res.body!)) { ... }
```

### 复杂度与边界

- **时间复杂度：** O(total_bytes) 单次扫描。
- **边界：** `[DONE]` 是 OpenAI 约定非标准 SSE；半包 `\n` 留 buffer；`\r\n` 需 normalize；断线重连带 `Last-Event-ID`（若后端支持）。

### 与前端工程结合的角度

- 与 Vercel AI SDK 的 `streamText` 对比：生产优先 SDK，面试能手写 parser 加分。
- tool_calls 增量 delta 需按 `index` 合并后再 JSON.parse。

### 面试加分项

- 说明 fetch SSE vs EventSource：POST body、自定义 header 必须用 fetch。
- 网关层勿 buffer 整个 SSE 响应，需 chunk 透传。

## 大批量数据求和（Map-Reduce，禁止塞入 LLM Context）

**来源：** 快手AI Agent开发一面

### 题目要点

- 1000 条数据求和：**不要让 LLM 心算**；Agent 理解意图 → 调用确定性代码 → 返回结果。
- 大数据分批 map-reduce，流式读取防 OOM。

### 可运行实现

```typescript
/** 分批求和：batchSize 控制内存；可接 CSV 流 */
export async function batchSum(
  numbers: number[],
  batchSize = 200,
): Promise<{ sum: number; batches: number }> {
  let sum = 0;
  let batches = 0;
  for (let i = 0; i < numbers.length; i += batchSize) {
    const chunk = numbers.slice(i, i + batchSize);
    sum += chunk.reduce((a, b) => a + b, 0);
    batches += 1;
  }
  return { sum, batches };
}

/** Agent tool handler：LLM 只调此函数，不读原始数组 */
export async function sumTool(args: { data: number[] }) {
  const { sum, batches } = await batchSum(args.data);
  return JSON.stringify({ sum, batches, count: args.data.length });
}
```

### 复杂度与边界

- **时间复杂度：** O(n)；**空间：** O(batchSize) 若流式则 O(1) 额外空间。
- **边界：** 空数组、NaN、溢出（BigInt / decimal.js）；100 万条应用 stream + worker，UI 展示 progress。
- **Agent 角色：** 选策略（sum / avg / groupBy）+ 解释结果；计算交给 code。

### 与前端工程结合的角度

- CSV 上传 → 后端 pandas / 此函数；前端 Progress（45/1000 batches）。
- WebSocket 推送 batch 完成事件。

### 面试加分项

- 对比 Temporal / Inngest durable workflow 处理长任务。
- 强调 Skill 中 for-loop 放 code node，不放 prompt。

## 工具调用统一封装（带重试与超时）

**来源：** 分享一下我面试Agent岗位时被问到的问题

### 题目要点

- 所有 tool 走统一 wrapper：超时、重试、结构化错误返回。
- 错误以 Observation 喂回 LLM，而非抛异常中断会话。
- 幂等操作 retry ≤2；非幂等禁止自动重试。

### 可运行实现

```typescript
function withTimeout<T>(ms: number, fn: () => Promise<T>): Promise<T> {
  return Promise.race([
    fn(),
    new Promise<never>((_, rej) =>
      setTimeout(() => rej(new Error("timeout")), ms)
    ),
  ]);
}

type ToolResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: string; retryable: boolean };

export async function runTool<T>(
  fn: () => Promise<T>,
  opts: { retries?: number; timeoutMs?: number } = {},
): Promise<ToolResult<T>> {
  const { retries = 2, timeoutMs = 30_000 } = opts;
  for (let i = 0; i <= retries; i++) {
    try {
      const data = await withTimeout(timeoutMs, fn);
      return { ok: true, data };
    } catch (e) {
      const error = e instanceof Error ? e.message : String(e);
      const retryable = error === "timeout" || /5\d{2}/.test(error);
      if (i === retries || !retryable) return { ok: false, error, retryable };
      await new Promise((r) => setTimeout(r, 500 * 2 ** i));
    }
  }
  return { ok: false, error: "unknown", retryable: false };
}

// ReAct 中：const obs = (await runTool(() => searchKb(q))).ok
//   ? data : `Error: ${error}`;  messages.push({ role: "tool", content: obs });
```

### 复杂度与边界

- **最坏等待：** O(retries × timeoutMs)。
- **边界：** 写操作 `retries=0`；需 idempotency key 防重复；备用 API 在 `retryable` 且主端点失败时切换。

### 与前端工程结合的角度

- 同样模式封装 BFF fetch；SSE 推送 `tool_error` + 单步重试按钮。
- 整体 Agent timeout 30s 与单 tool timeout 分层配置。

### 面试加分项

- 区分 4xx 不重试、5xx/timeout 可重试；OpenTelemetry 记录 attempt 次数。
- 面经要点：关键工具有备用 API 降级。

## 布隆过滤器（简易实现）

**来源：** 快手AI Agent开发一面

### 题目要点

- 位数组 + 多 hash；插入置位；查询全 1 则「可能存在」。
- 无 false negative；有 false positive；一般不支持删除。

### 可运行实现

```typescript
class BloomFilter {
  private bits: Uint8Array;

  constructor(
    private size: number,
    private hashCount: number,
  ) {
    this.bits = new Uint8Array(Math.ceil(size / 8));
  }

  insert(item: string) {
    for (const h of this.hashValues(item)) this.setBit(h);
  }

  mightContain(item: string): boolean {
    return this.hashValues(item).every((h) => this.getBit(h));
  }

  private hashValues(s: string): number[] {
    const out: number[] = [];
    for (let seed = 0; seed < this.hashCount; seed++) {
      let h = seed;
      for (let i = 0; i < s.length; i++) h = (h * 31 + s.charCodeAt(i)) % this.size;
      out.push(h);
    }
    return out;
  }

  private setBit(i: number) { this.bits[i >> 3] |= 1 << (i & 7); }
  private getBit(i: number) { return (this.bits[i >> 3] & (1 << (i & 7))) !== 0; }
}
```

### 复杂度与边界

- **时间复杂度：** O(k)，k=hashCount。
- **边界：** 容量饱和时误判率上升需重建；精确去重改用 Set；删除需求用 Cuckoo Filter。

### 与前端工程结合的角度

- 纯后端组件；理解即可解释「doc_id 可能已索引」的快速预判。

### 面试加分项

- 误判率与 m、n、k 关系；Agent 场景用于减少向量库 / DB 无效查询。
