# 小红书 AI Agent 面试题工具 · 项目说明

> 面向「资深前端 → AI Agent 转型求职」。每天自动从小红书搜集 AI Agent 面试题,整理成题库,用大模型作答并按主题归类为复习指南。

---

## 一、功能点

1. **抓取**:用已登录的小红书账号搜索 AI Agent 相关关键词,抓取面经/面试题笔记。
2. **题库**:把抓到的原始笔记按日期整理成 Markdown 题库。
3. **作答**:用大模型(当前 `cursor-agent`,跑你的 Cursor 订阅)逐题作答,视角固定为「资深前端转 Agent」。
4. **归类**:按主题去重合并成复习指南(含核心要点 / 前端结合 / 加分项 / 代码示例),并生成主题索引。
5. **定时**:配置化的 cron 调度,每天自动跑整条流水线,无人值守。

---

## 二、整体流程

```
cron(默认 23:20) → scripts/daily.sh → npm run daily
   │
   ├─ 阶段一 抓取(src/crawler)
   │    搜索关键词 → 取带 xsec_token 的笔记链接 → 进详情页抓标题+正文
   │    → 按 noteId 去重写入 data/notes.jsonl + 生成 docs/题库/YYYY-MM-DD.md
   │
   └─ 阶段二 作答(src/answerer)
        取「未作答」笔记 → 拼 prompt → 调 cursor-agent 提取题/去重/作答/归类
        → 写 docs/复习指南/<主题>.md → 标记已作答 → 重建 index.md
```

模块边界:`crawler`(抓)/ `store`(存与去重)/ `docs`(出 Markdown)/ `answerer`(答)/ `pipeline`(编排)/ `config`(配置)/ `schedule`(定时同步)。`pipeline` 把「抓取函数」和「回答器」以参数注入,因此核心逻辑可脱离网络和大模型做单元测试。

## 四、技术点

**语言 / 工程**
- Node.js + TypeScript(ESM,`"type":"module"`,本地 import 带 `.js` 后缀)
- Vitest 单测,核心模块走 TDD(去重、题库、索引、prompt、pipeline、schedule,共 17 个测试)
- 依赖注入提升可测性:`pipeline` 注入 `crawlFn` 与 `Answerer`,测试用假实现即可全覆盖

**抓取**
- Playwright(Chromium)**持久化登录态**:`launchPersistentContext` + `.auth/`,扫码一次长期复用
- 反爬:随机延时、每关键词限量、复用登录态
- 关键修复:小红书需用带 `xsec_token` 的 `/search_result/...` 链接才能加载正文(裸 `/explore/` 打不开)
- 登录失效检测:整轮 0 卡片即抛出明确提示,引导重新 `npm run login`
- 容错:逐笔记 try/catch + `finally` 关页面,单条失败不影响整体

**存储 / 去重**
- JSONL 追加存储;原始层按 `noteId` 精确去重,复习指南层由大模型做语义去重
- `answered` 标记 → 只对新题作答(幂等,重复运行不重复作答)

**作答(可插拔)**
- `Answerer` 接口 → 当前实现 `CursorAgentAnswerer`:`child_process.spawn` 调 `cursor-agent -p <prompt> --force`,跑 Cursor 订阅、无需额外 API key
- 预留 `claude` 实现,切换只改 `config.answerer`
- prompt 固化结构(核心要点 / 前端结合 / 加分项)+ 代码示例 + 中文约束 + 主题分类(含「手写代码题」)

**调度(配置化)**
- `config.schedule` 写 cron 表达式 → `npm run schedule` 幂等同步到系统 crontab(用 `# xhs-ai-interview-managed` 标记只管自己那行,不动用户其它任务)
- `scripts/daily.sh` 处理 cron 最小环境的 PATH(source nvm + `~/.local/bin`)

**环境踩坑**
- 国内网络拉不动 Playwright 官方 CDN → 改用 npmmirror 镜像,并锁 `playwright@1.45.x`(新版改用 Chrome-for-Testing 下载路径,镜像未同步)

## 五、Playwright 实现原理(详解)

### 5.1 它到底是什么
Playwright 是一个浏览器自动化框架。它**启动一个真实浏览器进程**,然后用代码通过**进程间的调试协议**远程操控这个浏览器(打开网页、查找元素、点击、输入、读取内容、拦截网络等)。因为驱动的是真实浏览器,会执行 JS、渲染 SPA、携带登录态,所以能抓到小红书这种「纯前端渲染 + 需登录 + 带 token」的页面——这是 `fetch`/`axios` 抓静态 HTML 做不到的。

### 5.2 分层架构

```
┌─────────────────────────────────────────────┐
│ 你的脚本 (Playwright Client, Node API)        │  page.click(), locator.textContent()
└───────────────┬─────────────────────────────┘
                │  Playwright 协议(JSON 消息,带 id 关联请求/响应)
┌───────────────▼─────────────────────────────┐
│ Playwright Driver / Server (Node, 随包内置)   │  把高层 API 翻译成浏览器协议命令、管理对象生命周期
└───────────────┬─────────────────────────────┘
                │  浏览器调试协议(Chromium: CDP;FF/WebKit: 定制协议)
┌───────────────▼─────────────────────────────┐
│ 真实浏览器进程 (Chromium / Firefox / WebKit)  │  实际执行导航、渲染、JS、DOM 操作
└─────────────────────────────────────────────┘
```

- **Client(客户端)**:你写的 `chromium.launch()`、`page.goto()` 等调用。
- **Server/Driver(服务端/驱动)**:Playwright 自带的一个用 Node/TS 实现的服务层,负责把高层语义翻译成底层协议命令、维护浏览器里各种对象(Page、Frame、ElementHandle)的引用、做自动等待等逻辑。多语言绑定(Python/Java/.NET)都是通过一条管道和这个 Node 服务端通信——这也是 Playwright 能跨语言、行为一致的原因;在 Node 里 client 和 server 基本同进程。
- **Browser(浏览器)**:Playwright 安装时会下载**特定版本的浏览器构建**(我们这次是 `chromium-1124`),保证协议兼容。对 Chromium 用 **CDP(Chrome DevTools Protocol)**;对 Firefox/WebKit 用的是 Playwright **打过补丁的定制构建**(暴露统一的、CDP 风格的协议,如 Firefox 的 Juggler),从而抹平三大引擎差异。

### 5.3 通信机制
- 浏览器和驱动之间是**双向、异步、消息式**的:每条命令是一个带唯一 `id` 的 JSON 消息(如 `Page.navigate`、`Runtime.evaluate`、`DOM.querySelector`),浏览器执行后用同一个 `id` 回传结果;同时浏览器会**主动推送事件**(如页面加载、网络请求、console 输出)。
- 传输通道通常是 WebSocket 或操作系统管道(pipe)。
- 这种「命令 + 事件」模型让 Playwright 既能下指令,也能监听页面发生的一切(网络拦截、对话框、新开标签页等)。

### 5.4 对象模型
- **Browser**:一个浏览器实例(一个进程)。
- **BrowserContext**:浏览器内相互隔离的「会话」,各自独立的 cookie/localStorage/缓存,类似「无痕多开」,测试之间互不污染。
- **Page**:一个标签页;**Frame**:页内的 iframe。
- **Locator**:对「如何定位元素」的惰性描述(不是元素本身),每次操作时才实时解析,天然适配动态 DOM。
- **ElementHandle**:对某个具体 DOM 节点的引用(较少直接用,Locator 更推荐)。

### 5.5 自动等待与可操作性检查(关键)
传统自动化(如老式 Selenium)常靠 `sleep` 硬等,易抖动。Playwright 在执行动作前会**自动等待**元素满足「可操作性(actionability)」:已附加到 DOM、可见、稳定(停止动画)、可交互、未被遮挡——满足才动手,否则在超时时间内不断重试(默认 30s)。

> 这正好解释了本项目之前的现象:抓裸 `/explore/<id>`(无 token)时正文节点 `#detail-title` 始终不出现,`textContent()` 就一直等到 **30 秒超时** 才报错。换成带 `xsec_token` 的链接后正文正常渲染,选择器立刻命中。

### 5.6 在页面里执行 JS:`evaluate`
`page.evaluate(fn)` 会把你的函数**序列化成源码**发给浏览器,在页面的 JS 上下文里(通过 CDP 的 `Runtime.evaluate`)运行,再把**可 JSON 序列化的返回值**传回 Node。注意:
- 该函数运行在浏览器里,拿不到 Node 作用域的变量(要显式通过参数传入)。
- 返回 DOM 节点这类不可序列化对象时,会返回句柄而非值。
- 本项目排查选择器时,就是用 `evaluateAll` 在页面里批量读取链接 `href`、遍历候选标题/正文节点。

### 5.7 持久化登录态
- 普通 `launch()` + `newContext()` 是「无痕」隔离的,关掉即清空。
- 本项目用 `launchPersistentContext(userDataDir)`:直接基于磁盘上的**真实用户数据目录**(`.auth/`)启动,cookie/localStorage 落盘持久化,所以**扫码登录一次,后续运行免登录**。
- (另一种做法是 `context.storageState()` 导出/导入登录态 JSON,本项目选了更省事的持久化目录方案。)

### 5.8 Headless / Headed
- 同一套代码可**无头(headless)**后台运行(cron/服务器适用),或**有头(headed)**弹出真实窗口便于调试(本项目登录时用有头扫码,把 `config.headless` 设为 `false` 也能肉眼看抓取过程)。
- 现代 Chromium 的新版无头模式与有头共用同一套渲染路径,行为差异已很小。

### 5.9 与 Puppeteer / Selenium 的关系
- **Puppeteer**:同样基于 CDP,但主要面向 Chromium;Playwright 由原 Puppeteer 团队主创,扩展到三大引擎,并强化了自动等待、多上下文、网络拦截、测试器等。
- **Selenium**:走 W3C WebDriver 协议、通过各浏览器的 driver(chromedriver 等)间接控制,历史更久、生态广,但自动等待等体验不如 Playwright 现代化。

### 5.10 小结(为什么本项目用它)
需要「带登录态、能渲染 SPA、能拿到 JS 动态生成内容」的抓取,Playwright 的真实浏览器驱动 + 持久化登录 + 自动等待,正好契合小红书这种反爬且前端渲染的站点;而它的无头模式又让整条流水线能在 cron 里无人值守地跑。

## 六、使用速查

```bash
npm run login        # 首次扫码登录小红书(有头)
npm run crawl        # 仅抓取 → data/notes.jsonl + docs/题库/今天.md
npm run answer       # 仅对未作答的题作答归类 → docs/复习指南/
npm run daily        # 抓取 + 作答(完整流水线)
npm run schedule     # 按 config.schedule 安装/更新定时任务
npm run schedule:off # 移除定时任务
```

依赖前提:`npx playwright install chromium`(国内可用 `PLAYWRIGHT_DOWNLOAD_HOST=https://cdn.npmmirror.com/binaries/playwright`)、`cursor-agent` 已安装并 `cursor-agent login`。
